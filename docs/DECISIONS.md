## 2026-11-02 하이브리드 검색(RRF) 0.8:0.2 채택, kiwi 사용자 사전 미채택 (#27)

**문제**: 임베딩과 BM25가 서로 다른 질문을 놓친다. 임베딩만 놓침: q007·q012·q030 (BM25는 4~5등), BM25만 놓침: q005·q022·q028 (임베딩은 1~2등). 둘을 합치면 서로 메울 거라고 봤다. #25에서 미룬 kiwi 사용자 사전 최종 결정도 여기서 한다.

**선택지**:
1. 임베딩 단독 (지금)
2. 하이브리드: 임베딩·BM25 후보 20개씩을 RRF(k=60)로 합친다. 임베딩 : BM25 가중치 0.8:0.2 / 0.5:0.5 / 0.2:0.8
3. 하이브리드 + kiwi 사용자 사전 (`terms.yaml` 28개)

**채택 기준** (실험 전에 정함, 이슈 #27 댓글):
- 임베딩 단독보다 등수가 오른 질문이 내려간 질문보다 3개 이상 많고, 회귀 Hit@5 100% 유지
- 동기가 된 q007·q012·q030을 빼고도 내려간 질문이 오른 질문보다 많지 않을 것
- 사전: 하이브리드 안에서 켬/끔, #25 기준(q007 제외, 차이 ≥ 3)
- 속도: 이슈 댓글에는 허용선을 두지 않았지만 `docs/DESIGN.md`의 "검색 시간 중간값 0.2초 이하"를 따른다
- 함께 확인: DESIGN 채택(능력 MRR 상승 + 회귀 Hit@5 유지), QA 9번(품질 지표 5%p 이상)

**결과** (노트 8개, 답없음 제외 48문항, 회귀 36 / 능력 12):

| 설정 | 오름 | 내려감 | 차이 | Hit@5 | Hit@1 | MRR | 회귀 Hit@5 | 능력 MRR |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 임베딩 단독 | | | | 94% | 73% | 0.813 | 100% | 0.294 |
| 하이브리드 0.8:0.2 | 4 | 1 | +3 | 94% | 75% | 0.822 | 100% | 0.354 |
| 하이브리드 0.5:0.5 | 6 | 2 | +4 | 94% | 71% | 0.806 | 97% | 0.392 |
| 하이브리드 0.2:0.8 | 7 | 11 | −4 | 98% | 54% | 0.711 | 97% | 0.489 |
| BM25 단독 (참고) | 6 | 14 | −8 | 94% | 50% | 0.667 | 94% | 0.385 |

(사전 끔 기준. 0.5:0.5는 사전 켬이면 Hit@1 73%·MRR 0.817, 오름/내려감은 사전 켬 기준)

- 0.8:0.2에서 바뀐 질문: q006 5→3등, q021 4→3등, q022 2→1등, q035 2→1등, q005 1→5등. 동기 3개를 빼도 오름 4 / 내려감 1
- 동기가 된 q007·q012·q030은 0.8:0.2에서 하나도 못 고쳤다. BM25 비중을 키우면 q030(0.5, 0.2)·q012(0.2)가 들어오지만 q005 "bias는 무슨 역할이야?"가 5등 밖으로 밀려 회귀 100%가 깨진다
- 사전 켬/끔: 0.8:0.2에서 바뀐 질문 0개(모든 수치 같음). 0.5:0.5는 q032 2→1등 하나, 0.2:0.8은 q043 3→1등·q007 4등→밖. 모두 기준(≥ 3) 미달
- 속도 (검색 시간 중간값, 55문항 × 3회): 임베딩 30ms, BM25 0.2ms, 하이브리드 0.8 30ms. BM25가 거의 공짜라 하이브리드도 임베딩과 같다. 0.2초 이하
- 비용: 0원 (LLM 호출 없음)

**결정**:
- 하이브리드 0.8:0.2 채택. 이슈 기준(+3), DESIGN 채택(능력 MRR 0.294 → 0.354, 회귀 100%), QA 9번(능력 MRR +6%p), 속도(30ms)를 모두 통과한다. `evaluate.py` 기본값과 CI 회귀 평가를 하이브리드로 바꿨다 (`embedding`, `bm25` 인자로 한쪽만 채점 가능)
- kiwi 사용자 사전 미채택. `terms.yaml`, 등록 코드, `noterms` 옵션, pyyaml 의존성을 뺐다

**버린 이유**:
- 임베딩 단독: 하이브리드가 같은 속도·비용으로 능력 MRR을 올린다.
- 0.5:0.5, 0.2:0.8: 회귀 Hit@5가 97%로 떨어진다 (q005).
- kiwi 사용자 사전: 채택한 0.8:0.2에서 결과가 전혀 바뀌지 않는다. #25 BM25 단독에서도 차이 2였다. kiwi가 대부분 같은 방식으로 잘라 맞춰 줄 게 적다. 노트가 크게 늘면 다시 잴 수 있게 단어 목록을 남긴다: 신경망, 매개변수, 합성곱, 하이퍼파라미터, 특징, 미분, 과대적합, 임계값, 분포, 풀링, 전처리, 미니배치, 출력층, 소프트맥스, 경사법, 드롭아웃, 가중합, 유사도, 스트라이드, 음수, 유의어, 서브워드, 경사하강법, 항등, 자연어, 순전파, 역전파, 국소
- 한계: 차이 +3은 기준선에 딱 걸친다. 48문항에서 3문항은 6%p라 잡음과 구분이 크지 않다. 노트·질문이 늘면 다시 잰다.

## 2026-10-29 kiwi 사용자 사전: BM25 단독 기준 미달, 하이브리드에서 다시 결정 (#25)

**문제**: q007 "임계값"을 보고, kiwi가 같은 단어를 위치에 따라 다르게 잘라(임계값 / 임계+값) BM25가 놓친다고 봤다. 다시 확인하니 노트에서 "임계값" 15번 중 14번, 질문에서도 `임계 + 값`으로 똑같이 잘렸고, BM25는 q007 정답을 이미 4등에 넣고 있었다.

**선택지**:
1. 사전 없음
2. `terms.yaml` 단어를 kiwi 사용자 사전에 등록. 후보는 노트에서 위치에 따라 다르게 잘리는 명사 29개를 자동으로 뽑고(평가셋은 보지 않음), 사람이 28개를 골랐다

**채택 기준** (실험 전에 정함): BM25 기준, q007을 빼고 등수가 오른 질문이 내려간 질문보다 3개 이상 많으면 채택. q007은 이 작업을 시작하게 한 질문이라 뺀다 (절대 원칙 7).

**결과** (노트 8개, 답없음 제외 48문항, BM25):

| 질문 | 사전 끔 | 사전 켬 |
| --- | --- | --- |
| q013 분류문제에서는 어떤 함수를 사용해? | 5등 | 4등 |
| q032 합성곱 계층의 필터의 역할은 무엇인가? | 3등 | 2등 |
| q043 자연어 | 3등 | 1등 |
| q010 역전파 | 3등 | 4등 |
| q007 임계값 (판정 제외) | 4등 | 5등 |

- q007 제외 47문항: 오름 3, 내려감 1, 차이 2. Hit@5 94% → 94%, Hit@1 51% → 53%, MRR 0.68 → 0.69
- q007은 오히려 내려갔다. "임계값"이 한 덩어리가 되자 그 단어가 많은 논리 게이트 섹션과 "2. 가중치 > 방향"이 앞섰다. q010도 "역전파"가 여러 섹션에서 똑같이 잡혀 정답 섹션이 밀렸다
- 임베딩 검색은 영향 없음 (CI 회귀 평가 그대로)

**결정**: BM25 단독으로는 기준 미달(차이 2 < 3)이라 채택하지 않는다. 다만 BM25는 하이브리드 안에서 쓰이므로 최종 결정은 하이브리드에서 사전 켬/끔을 다시 비교해 정한다. 그때까지 `terms.yaml`과 등록 코드는 남겨 둔다. BM25는 아직 실제 검색에 쓰이지 않아(`evaluate.py bm25` 비교용) 남겨 둬도 영향이 없다.

**버린 이유**:
- 지금 바로 되돌리기: 사람이 고른 단어 목록을 다시 만들기 번거롭고, BM25가 쓰이는 곳(하이브리드)에서 재 보기 전에 버리기는 이르다. 하이브리드에서도 기준 미달이면 그때 뺀다.

## 2026-10-23 Anthropic 블로그 구조로 기획 재설계 (#17)

**문제**: 기획이 모듈을 계속 더하는 방향으로 커져, 지금 규모(노트 6개, 주 5문제)에 비해 쓰이지 않는 모듈과 실험이 많았다. 출제 방식 셋, 리랭커, 날짜 필터, 컨텍스트 압축, 노트 인젝션 실험, 서버(FastAPI + Railway)가 근거 없이 계획에 들어 있었다.

**선택지**:
1. 기존 기획에서 쓰이지 않는 것만 뺀다 (기획안 v2)
2. Anthropic 엔지니어링 블로그의 구조 개념으로 처음부터 다시 짠다 (기획안 v7, `docs/PLAN.md`)

**결정**: 2번. 주요 변경:
- 구조: Brain · Hands · Session 분리. Brain은 키워드 선택 Agent 1개 + Workflow 2개(Prompt chaining + 게이트, Evaluator-optimizer). 프레임워크(LangGraph) 없이 Claude API로 직접 짠다
- 출제: 인용 기반 생성. 인용문이 원문에 있는지 코드가 검사하고, 분리된 평가자가 항목별 통과/미달로 채점한다 (1~5점 점수 대신)
- 생성량: 주 5문제 = 평일 발송 5통. 검토 화면에서 답은 접어 둔다
- 평가: 회귀 평가셋(Hit@5 유지, PR마다 CI) / 능력 평가셋(MRR 상승)으로 나눈다
- 중심 실험: 노트 통째로 넣기 vs RAG 교차점
- 발송: FastAPI + Railway 대신 GitHub Actions. 서버에 LLM·Claude API 키 없음
- 뺀 것: 꼬리질문 웹 검색, `[노트 밖]` 꼬리질문, 자동 승인, 멀티 에이전트, Routing, Parallelization, 메타데이터 날짜 필터 실험, 노트 인젝션 실험, Docker, Q&A 도우미 Phase(Citations API와 함께 조건부). LangGraph는 같은 루프를 옮겨 보는 비교 대상으로만 둔다
- 조건부: 리랭커, 컨텍스트 압축, Voyage 임베딩
- 키워드: ① 멀티모달 전처리 ② 에이전틱 RAG ③ RAG 최적화 ④ 툴콜링·평가. ⑤ VLM 파인튜닝, ⑥ Function Calling 멀티턴 파인튜닝은 제외, ⑦ 임베딩 파인튜닝은 보너스

**버린 이유**:
- 1번: 모듈 목록을 줄이는 데 그치고, 무엇을 왜 쓰는지에 대한 근거가 없다. 블로그 개념(Simplicity, 측정 후 추가)을 뼈대로 삼으면 넣고 빼는 기준이 하나로 정리된다.

## 2026-10-21 실험 시작 기준을 노트 50개에서 10개로 변경 (#14)

**문제**: 노트를 하루 하나씩 직접 정리하다 보니 앞으로 많아야 20개 정도라, 50개를 기다리면 Phase 2 실험을 시작할 수 없다.

**선택지**:
1. 50개 유지
2. 10개에서 1차(잠정) 실험, 20개에서 확정
3. 10개에서 실험하고, 판단이 어려우면 평가셋 질문을 늘린다

**결과**: 노트 10개면 질문 약 60개, 메인(키워드) 약 20개다. 채택 기준 "새로 맞힘 − 새로 틀림 ≥ 3"은 메인 20개에서 15%p 차이라 작은 개선은 놓칠 수 있다.

**결정**: 3번. 노트 10개 이상 쌓이면 실험한다. 메인 질문이 적어 판단이 어려우면 평가셋 질문(키워드 등)을 늘린다. 기능 구현은 노트 개수와 상관없이 한다.

**버린 이유**:
- 1번: 노트 50개는 현실적으로 쌓기 어렵다.
- 2번: 같은 실험을 두 번 돌리는 것보다, 질문을 늘려 한 번에 판단하는 쪽이 단순하다.

## 2026-10-15 데이터와 메일 형식 방향 전환 (#9)

**문제**: AI로 정리한 강사 자료 노트가 내 것 같지 않고, `> 메모:` 245개 중 121개가 자료 오타 지적이라 출제 우선순위 신호로 쓸 수 없었다. 강사 자료는 공개 저장소에 올리기도 어렵다.

**선택지**:
1. 기존 노트 유지 + 내 노트 추가
2. 기존 노트 제외, 직접 정리한 노트(손필기 사진 + Notion)만 사용

**결과** (퍼셉트론 노트 1개 시범):
- 손필기 3장 + Notion 정리 → 노트 1개, 형식 검사 통과, 청크 13개
- 기존 노트 20개와 함께 색인했을 때 "가중치는 왜 손실을 줄이는 방향으로 바꿔?"에 새 노트 섹션이 1등
- 같은 개념이 두 노트에 있으면 상위 5개를 나눠 가짐 → 평가셋 정답은 목록으로 저장해야 함
- AND 게이트 질문에 OR 게이트가 1등 (표·문장이 비슷한 청크) → BM25 비교 후보

**결정**: 2번. 기존 노트 20개와 평가셋 12개는 프로젝트 밖에 보관하고, 오늘부터 직접 정리한 노트를 쌓는다. 함께 정한 것:
- 메일: 질문 1개 + 답(노트 근거) / 꼬리질문 1개(답 없음, 스스로 생각해 보기). 꼬리질문은 노트 안에서 먼저 연결하고 없으면 웹 검색, `[노트 밖]` 표시와 출처 링크
- 노트 합치는 규칙: 손필기가 뼈대, Notion 정의는 섹션 첫 줄, 고쳐 쓰지 않음, 그림은 글로
- 사진 변환 원본은 고치기 전에 따로 저장 (변환 품질 비교)
- KV cache·Prefill은 Phase 3에서 프롬프트 캐싱으로 반드시 측정 (비용, 첫 글자까지 시간, 캐시 적중 토큰)
- 다룰 키워드에서 Function Calling 멀티턴 파인튜닝은 제외
- Phase 3 첫 작업: Claude 호출 로그(토큰 수, 캐시 토큰, 첫 글자까지 시간)를 남기는 코드
- 이후 실험 후보: 꼬리질문 노트만 vs 노트+웹 검색, 사진 변환 모델 비교(고친 글자 수·비용·속도), 꼬리질문 중 `[노트 밖]` 비율이 노트가 쌓이며 줄어드는지
- 노트 입력 화면(Streamlit)은 손으로 몇 주 해 본 뒤 만든다

**버린 이유**:
- 1번: 노트가 섞여 있으면 출제 우선순위와 공개 범위를 계속 구분해야 하고, 직접 쓴 노트의 장점(내 질문, 직접 확인한 내용)이 묻힌다. 대가로 노트 50개까지 실험이 늦어지는 것은 감수한다.
