## 제약

- 서버(GitHub Actions)에는 LLM, 벡터DB, 임베딩 모델, Claude API 키를 두지 않는다. 승인된 문제 텍스트만 올린다.
- 노트 파일은 수정하지 않는다. `topic`, `keywords`는 따로 저장한다.
- 질문·답·꼬리질문의 근거는 노트에만 둔다. 답에는 원문 인용을 붙이고, 인용할 수 없으면 출제하지 않는다 ("기록 비어 있음").
- 노트는 `<documents>` 태그로 감싸 자료로만 다룬다. 출력은 구조화된 출력으로만 받는다.
- 받는 메일 주소는 코드에 고정한다. 메일 키는 발송 전용 권한으로 GitHub Secrets에만 둔다.
- 실험은 노트 10개 이상 쌓인 뒤에 한다. 메인 질문이 적어 판단이 어려우면 평가셋 질문을 늘린다. 기능 구현은 노트 개수와 상관없이 한다.

## 평가자 기준표

생성자와 평가자에게 같이 준다. 항목별 통과/미달/판단 불가로 판정하고, 하나라도 미달이면 탈락이다. 판단 불가는 표시 후 사람에게 보낸다.

| 평가 항목 | 통과 조건 | 미달 예시 |
| --- | --- | --- |
| 답-인용 일치 | 답의 모든 내용이 인용문에서 확인된다 | 인용문에 없는 이유가 답에 있다 |
| 명확함 | 무엇을 답해야 하는지 하나로 정해진다 | "~에 대해 설명하라" |
| 난이도 | 이유·비교·관계를 묻는다 | "편향이란 무엇인가?" |
| 꼬리질문 전제 | 깔고 있는 사실이 노트와 맞다 | 노트와 다른 사실을 전제로 묻는다 |

코드가 보는 항목(게이트 2): 형식, 중복(기존 문제와 임베딩 유사도), 인용문이 원문에 글자 그대로 있는지.

## 운영 수치

- 주말에 5문제 생성, 사람 검토. 검토 화면에서 답은 접어 두고 질문 품질만 본다. 단축키로 승인/거절/수정.
- 거절 사유: 너무 쉬움 / 기록에 없음 / 애매함 / 중복 / 꼬리질문 전제 틀림. 사유는 출제 상태에 저장해 Agent가 참고한다.
- 평일 하루 1통(질문 + 답 + 원문 인용, 꼬리질문 1개) 발송, 주말 미발송. 메일 끝에 누적 발송 수 문구 (예: "오늘로 37번째 복습, 머릿속에 차곡차곡.").
- 승인 큐(`queue/approved.json`)는 섞어서 발송 날짜를 미리 붙인다. 발송 작업은 큐를 읽기만 한다.
- 남은 발송분 10개 미만이면 알림.
- 루프 통제: 키워드 선택 도구 호출 최대 3회, 문제당 LLM 호출 최대 10번, 게이트 2 실패 1회 재시도, 평가자 미달 1회 재생성.

## 평가셋

| 평가셋 | 무엇 | 지표 | 역할 |
| --- | --- | --- | --- |
| 회귀 평가셋 | 지금 맞히는 질문 | Hit@5 | 새 모듈이 기존 성능을 깨지 않는지. PR마다 CI |
| 능력 평가셋 | Hit@1 실패 질문 전부 + 어려운 질문 5개 + 근거 없는 키워드 5개 (확정 필요) | MRR. 근거 없는 키워드는 "결과 없음"이면 정답 | 새 모듈을 채택할지 |
| 생성 판정 기록 | 모든 문제의 사람 판정과 평가자 판정 | 인용 일치율, 평가자-사람 일치율, 승인율 | 생성 쪽 평가셋 |

- 유형: 키워드(출제할 때 고를 법한 개념 이름) / 문장(문장으로 물음, 노트에 답이 있음) / 비교(두 용어를 비교) / 한영혼용(노트는 한글, 질문은 영어) / 답없음(노트에 없는 질문).
- 파일: `eval/retrieval.csv` (id, query, type, answers, memo). 정답은 청크 id, 여러 개면 `;`로 구분. 회귀/능력 구분 방식은 (확정 필요).
- 사람이 쓴 100개 (노트 약 17개).
- 평가셋은 색인 대상에서 뺀다.

## 평가 기준

1. 맞음: 검색 결과 5개 안에 정답 섹션이 있으면 맞음 (Hit@5). MRR은 첫 정답 순위의 역수 평균. 키워드의 정답은 그 개념을 설명하는 섹션. (비교는 정답 전부, 답없음은 검색 점수 제외) 점수는 평가셋·유형별로 본다.
2. 공정: 평가셋에 질문과 정답을 먼저 다 적어 두고, 점수를 낸 뒤에는 정답을 바꾸지 않는다. 빠뜨린 정답을 고칠 때는 memo에 날짜와 이유를 남기고 다시 잰다. 점수를 비교할 때는 평가셋과 노트는 그대로 두고, 검색 방법 하나만 바꾼다. 실패 사례를 보고 고친 변경은 그 사례를 뺀 질문으로도 확인한다.
3. 채택: 능력 평가셋 MRR이 오르고 회귀 평가셋 Hit@5가 유지되면 넣는다.
   - 최소 차이는 실험 전에 정한다 (확정 필요).
   - 평가 질문 20개 수준이면 3문항 미만 차이는 잡음으로 본다 (20개에서 3개 = 15%p). 이보다 작은 차이는 구분할 수 없다는 한계를 기록한다.
   - 회귀 평가셋에서 새로 틀린 질문이 생기면 먼저 열어 본다.
   - 검색 시간(중간값)이 0.2초를 넘으면 넣지 않는다.
   - 프롬프트·캐시·모델을 바꾸면 회귀 평가를 다시 돌리고, 통과 못 하면 되돌린다.
