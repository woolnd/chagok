## 제약

- 서버에는 벡터DB와 임베딩 모델을 두지 않는다.
- 노트 파일은 수정하지 않는다. `topic`, `keywords`는 따로 저장한다.
- 노트에 근거가 없으면 출제하지 않는다 ("기록 비어 있음").
- 단, 답을 주지 않는 꼬리질문은 노트 밖에서도 낼 수 있고 `[노트 밖]` 표시와 출처 링크를 붙인다.
- 노트는 태그로 감싸 자료로만 다룬다. 출력은 정해진 구조로만 받는다.
- 5%p 미만 차이는 개선으로 보지 않는다. 판정은 아래 "평가 기준".
- 실험은 노트 10개 이상 쌓인 뒤에 한다. 메인 질문이 적어 판단이 어려우면 평가셋 질문을 늘린다. 기능 구현은 노트 개수와 상관없이 한다.

## 운영 수치

- 주말 검토: 주 15개, 5분 이내. 단축키로 승인/거절/수정.
- 거절 사유: 너무 쉬움 / 기록에 없음 / 애매함 / 중복 / 꼬리질문 전제 틀림.
- 평일 하루 1통(질문 + 답, 꼬리질문 1개) 발송, 주말 미발송. 메일 끝에 누적 발송 수 문구 (예: "오늘로 37번째 복습, 머릿속에 차곡차곡.").
- 주당 8~10개 생성 (초기 15개). 승인 후 2~3주 보관 뒤 발송.
- 남은 발송분 10개 미만이면 알림.

## 평가셋

| 구분 | 기능 | 검색에 넣는 것 | 노트당 |
| --- | --- | --- | --- |
| 메인 | 복습 메일 | 키워드 | 키워드 2 |
| 보조 | Q&A 도우미 | 질문 | 문장 1 · 비교 1 · 한영혼용 1 · 답없음 1 |

- 유형: 키워드(출제할 때 고를 법한 개념 이름) / 문장(문장으로 물음, 노트에 답이 있음) / 비교(두 용어를 비교) / 한영혼용(노트는 한글, 질문은 영어) / 답없음(노트에 없는 질문).
- 파일: `eval/retrieval.csv` (id, query, type, answers, memo). 정답은 청크 id, 여러 개면 `;`로 구분.
- 사람이 쓴 100개 (노트 약 17개).
- 답없음 문항은 검색 점수에서 빼고, Phase 6 Q&A 도우미가 "기록 없음"이라고 답하는지 볼 때 쓴다.

## 평가 기준

1. 맞음: 검색 결과 5개 안에 정답 섹션이 있으면 맞음. 키워드의 정답은 그 개념을 설명하는 섹션. (비교는 정답 전부, 답없음은 점수 제외) 점수는 메인·보조·유형별로 본다.
2. 공정: 평가셋에 질문과 정답을 먼저 다 적어 두고, 점수를 낸 뒤에는 정답을 바꾸지 않는다. 빠뜨린 정답을 고칠 때는 memo에 날짜와 이유를 남기고 다시 잰다. 점수를 비교할 때는 평가셋과 노트는 그대로 두고, 검색 방법 하나만 바꾼다.
3. 채택: 메인 Hit@5로 판정한다. 켰을 때 새로 맞힌 질문이 새로 틀린 질문보다 메인 답 있는 질문 수의 5%(올림) 이상, 최소 3개 이상 많으면 넣는다 (예: 메인 34개면 3개 이상).
   - 메인이 순손실이면 넣지 않는다.
   - 메인 순증이 0~2개여도, 보조가 같은 기준(5% 올림, 최소 3개)을 넘게 오르면 넣는다.
   - 검색 시간(중간값)이 0.2초를 넘으면 넣지 않는다.
   - 새로 틀린 질문이 3개 이상이면 먼저 열어 본다.
   - 근거: 문항 수가 적어 1~2개 변동은 우연일 수 있어 둔 경험적 기준이다 (통계 검정 아님). 평가셋이 커지면 다시 정한다.
